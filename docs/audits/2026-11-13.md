# Audyt wydajności i skalowalności `konuzastro-tracker` — seria C

Data: 13 listopada 2026. Baza: `main` w `91a3856` plus niezacommitowana zmiana `src/components/SkyDome.tsx` (rozmiary płócien w stylu); build i pomiary ją zawierają. ## Wynik

- **Jeden problem krytyczny, potwierdzony pomiarem.** C01: każde otwarcie i zamknięcie okna „Pozycja 3D” zostawia w pamięci całą poprzednią scenę. Przyczyna: `OrbitControls` z three r186 nie zdejmuje listenera `keydown` z `document`, bo React 19 odłącza DOM przed sprzątaniem `useEffect`. Ten sam mechanizm występuje w Obserwatorium. Naprawa to kilka linii.
- **Trzy wysokie:**
  - C02: kopuła przerysowuje się w całości przy każdym zdarzeniu kółka i przeciągania. Przerysowanie kosztuje ok. 20–25 ms JS, więcej niż budżet klatki. Droga Mleczna i maska ziemi liczą się przy tym od zera.
  - C03: w całej aplikacji nie ma Error Boundary. Błąd WebGL albo nieudane pobranie chunku daje biały ekran wszystkich zakładek.
  - C04: serwer produkcyjny nie kompresuje odpowiedzi i nie wysyła `ETag`. Każdy start pobiera ok. 2,7 MB danych zamiast ok. 0,8 MB.
- **Średnie:** osiem (C05–C12). **Niskie:** zebrane w tabeli. Odrzucone fałszywe alarmy opisano z pomiarem.
- **Zakładki nie kumulują pamięci.** Po 25 przełączeniach sterta i listenery są stałe, a kontekst WebGL kopuły jest zwalniany. Jedynym źródłem narastania pamięci w sesji jest okno 3D (C01).
- **Stan bazowy jest zielony:** `npm test` **406/406 w 56 plikach**, `npm run build` (z `tsc`) przechodzi.

## Znaleziska

### Krytyczne

**C01 — wyciek całej sceny przy każdym zamknięciu okna „Pozycja 3D”; także Obserwatorium.** Potwierdzone pomiarem i ścieżką zatrzymania.

Miejsca:
- `src/components/Space3D.tsx:157` (tworzenie kontrolek), `:170` i `:1043` (`controls.dispose()` w sprzątaniu `useEffect`);
- `src/components/observatory/scene.ts:181` i `:813`, wywołanie z `src/components/observatory/Observatory.tsx:107–111`;
- `node_modules/three/examples/jsm/controls/OrbitControls.js:505–506` i `:525–527`.

```js
// OrbitControls (three r186): connect() i disconnect()
const document = this.domElement.getRootNode(); // offscreen canvas compatibility
document.addEventListener( 'keydown', this._interceptControlDown, { passive: true, capture: true } );
…
const document = this.domElement.getRootNode();
document.removeEventListener( 'keydown', this._interceptControlDown, { capture: true } );
```

- **Mechanizm.** Przy tworzeniu kontrolek płótno jest już w dokumencie, więc listener trafia na `document`. Przy zamknięciu okna React 19 najpierw odłącza DOM portalu, a dopiero potem wywołuje sprzątanie `useEffect`. Wtedy `getRootNode()` zwraca odłączony `div` okna i `removeEventListener` trafia w niego. Listener zostaje na `document`.
- **Co jest trzymane.** Listener to metoda związana z `OrbitControls`. Przez listener `start` (`Space3D.tsx:498`) trzyma kontekst domknięcia efektu, a z nim całą scenę: tablice punktów, tekstury podpisów z ich płótnami i DOM okna. Ścieżka zatrzymania z migawki produkcyjnej:

  ```
  HTMLDocument → … → EventListener → native_bind (bound_this: OrbitControls) → _listeners.start[0]
    → context → … children → material.map.source.data = <canvas 214×64>
  ```

- **Dowody.** Krzywa w buildzie produkcyjnym, sterta po wymuszonym GC:

  | Pomiar | Start | Cykl 1 | Cykl 10 |
  |---|---:|---:|---:|
  | Sterta | 16,7 MB | 23,9 MB | 55,4 MB |
  | Listenery | 209 | 374 | 455 |
  | Węzły DOM | 640 | 736 | 1564 |

  `LayoutObjects` jest stałe (572), więc przybywające węzły są odłączone. Wariant z oknem otwartym 2 s zamiast 9 s daje to samo (55,1 MB po 10 cyklach). Wyciek powstaje więc przy montowaniu, a nie podczas intro.

  Po każdym cyklu na `document` przybywa jeden listener `keydown` (capture). Przechwycone wywołanie `removeEventListener` trafia w `DIV (isConnected=false)` (`doclisteners.mjs`). Konteksty WebGL są zwalniane (`forceContextLoss`), więc wycieka pamięć CPU, a nie GPU.
- **Obserwatorium.** Ten sam mechanizm potwierdzono w kodzie, bez pomiaru: świeży profil nie miał projektu zdjęcia. Płótno jest w `host` przy tworzeniu kontrolek (`scene.ts:178–181`), a `dispose()` woła sprzątanie `useEffect` po odłączeniu DOM.
- **Wpływ.** Pamięć rośnie liniowo z liczbą otwarć głównej funkcji 3D: ok. 100 MB po 30 otwarciach. Rosną też pauzy GC, które odczuwa cała aplikacja. Na telefonie karta zostanie w końcu ubita.
- **Naprawa.** Zdjąć listener, póki DOM jest podłączony. React wywołuje sprzątanie `useLayoutEffect` przy odmontowaniu **przed** usunięciem węzłów, a sprzątanie `useEffect` po nim.

  Przed (`Space3D.tsx`):
  ```tsx
  useEffect(() => {
    // …
    const controls = new OrbitControls(camera, renderer.domElement)
    const disposables: { dispose(): void }[] = [renderer, controls]
    // …
    return () => { /* … */ disposables.forEach((d) => d.dispose()) /* … */ }
  }, [hasObject, scale, withDistance, select, typeRGB])
  ```

  Po:
  ```tsx
  const controlsRef = useRef<OrbitControls | null>(null)
  // OrbitControls zdejmuje listener Ctrl z getRootNode() płótna. React odłącza DOM przed sprzątaniem useEffect,
  // więc wtedy trafiłby w odłączony fragment i listener zostałby na document razem z całą sceną.
  useLayoutEffect(() => () => controlsRef.current?.disconnect(), [])

  useEffect(() => {
    // …
    const controls = new OrbitControls(camera, renderer.domElement)
    controlsRef.current = controls
    // … sprzątanie bez zmian: dispose() woła disconnect() drugi raz, co jest bezpieczne.
  }, [hasObject, scale, withDistance, select, typeRGB])
  ```

  W Obserwatorium wystarczy zmienić sprzątanie w `Observatory.tsx:107` z `useEffect` na `useLayoutEffect`. Całe `dispose()`, w tym usunięcie płótna, wykona się wtedy przed odłączeniem DOM.

  Alternatywa bez zależności od kolejności Reacta: zapamiętać `renderer.domElement.getRootNode()` przy tworzeniu i po `dispose()` jawnie zdjąć z niego `controls._interceptControlDown`. Odradzam, bo używa prywatnego pola three.
- **Ryzyko zmiany.** Małe. Przy zmianie skali (bez odmontowania) sprzątanie działa jak dotąd, bo DOM jest wtedy podłączony.

**C03 — brak Error Boundary i obsługi utraty WebGL poza kopułą: biały ekran całej aplikacji.** Potwierdzone grepem i kodem. Łączy K13, P1, N10, D4, D5 i O8.

- **Stan.** W `src` nie ma `ErrorBoundary`, `getDerivedStateFromError`, `componentDidCatch` ani `vite:preloadError`. `webglcontextlost` obsługuje tylko `SkyDome.tsx:557`.
- **Scenariusze:**
  - `new THREE.WebGLRenderer(…)` (`Space3D.tsx:149`) rzuca, gdy WebGL jest niedostępny: wyłączona akceleracja sprzętowa, GPU na czarnej liście albo przeglądarka bez WebGL2. Wyjątek z efektu bez granicy błędów sprawia, że React 19 odmontowuje cały korzeń. Znika Niebo, Katalog i Planer.
  - Nieudane pobranie leniwego chunku (`App.tsx:7–10`, `SkyView.tsx:13`) przy zerwanym łączu daje ten sam skutek.
  - Space3D i Obserwatorium po utracie kontekstu GPU zostają z pustym płótnem bez odtworzenia.
- **Naprawa.** Klasowy `ErrorBoundary` na dwóch poziomach: wokół treści zakładki (z `key={tab}` resetuje się przy zmianie zakładki) i wokół okna 3D. Do tego `vite:preloadError` z jednorazowym przeładowaniem strony oraz nasłuch `webglcontextlost` w Space3D i Obserwatorium. Nasłuch musi pomijać utratę wywołaną przez własne `forceContextLoss()` przy sprzątaniu.

  Przed (`App.tsx:58–66`):
  ```tsx
  <main className="page" key={tab}>
    <div className="view-enter">
      <Suspense fallback={<div className="empty">Wczytywanie…</div>}>
        {tab === 'sky' && <SkyView />}
        …
  ```

  Po:
  ```tsx
  class ViewBoundary extends Component<{ children: ReactNode }, { error: Error | null }> {
    state = { error: null as Error | null }
    static getDerivedStateFromError(error: Error) { return { error } }
    render() {
      if (!this.state.error) return this.props.children
      // React.lazy pamięta odrzucony import, więc ponowny render rzuciłby ten sam błąd: ponowienie przeładowuje stronę
      // (stan i tak jest w localStorage).
      return <div className="empty">Nie udało się wyświetlić widoku. <button className="button small" onClick={() => location.reload()}>Wczytaj ponownie</button></div>
    }
  }
  // main.tsx: nowa wersja po wdrożeniu usuwa stare chunki; raz przeładuj zamiast białego ekranu.
  window.addEventListener('vite:preloadError', () => { if (!sessionStorage.getItem('reloaded')) { sessionStorage.setItem('reloaded', '1'); location.reload() } })

  <main className="page" key={tab}>
    <div className="view-enter">
      <ViewBoundary>
        <Suspense fallback={<div className="empty">Wczytywanie…</div>}>…</Suspense>
  ```

- **Ryzyko zmiany.** Małe.

**C04 — serwer produkcyjny: brak kompresji, `ETag` i `Last-Modified`; dane pobierane w całości przy każdym starcie.** Potwierdzone pomiarem nagłówków. Rozszerza otwarte B20 (ETag). Łączy S9 i K19.

Miejsca: `server/index.ts:48–51` i `vite.config.ts:50–55` (`StaleWhileRevalidate` dla `/data/`).

| Ścieżka | Rozmiar | `Content-Encoding` | `ETag` | `Cache-Control` |
|---|---:|---|---|---|
| `/data/catalog.json` | 1529 KB | brak | brak | `no-cache` |
| `/data/outlines.json` | 986 KB | brak | brak | `no-cache` |
| `/data/sky.json` | 194 KB | brak | brak | `no-cache` |
| `/assets/index-*.js` | 342 KB | brak | brak | `immutable` |

- **Mechanizm.** `no-cache` bez walidatora wymusza pełne pobranie, bo serwer nie ma czym odpowiedzieć 304. Service worker podaje dane z pamięci od razu, ale `StaleWhileRevalidate` przy każdym starcie pobiera w tle pełne 2,7 MB.
  - Przy pierwszej wizycie, w trybie prywatnym albo po wyczyszczeniu pamięci przez system telefonu pobranie blokuje katalog.
  - Startowy JS idzie jako 446 KB zamiast 158 KB gzip.
  - `vite preview` kompresuje (w `measure.log` transfer 418 KB dla `catalog.json`), więc pomiary na `preview` ukrywają problem.
- **Wpływ.** Każdy start na łączu komórkowym w terenie. Prekeszowanie przez service worker (1,6 MB, w tym chunk 3D) też idzie bez kompresji.
- **Warunek.** Problem znika, jeśli przed serwerem stoi proxy kompresujące (nginx, Caddy, Cloudflare). W repozytorium nie ma jego konfiguracji (`docs/uruchomienie.md`).
- **Naprawa.**
  1. Wstępna kompresja przy buildzie: `.br` i `.gz` dla `.js`, `.css`, `.json`, `.html` i `.svg` powyżej 1 KB, bez kompresji w czasie żądania, która blokowałaby pętlę zdarzeń.
  2. Negocjacja `Accept-Encoding` w serwerze.
  3. Słaby `ETag` z rozmiaru i czasu modyfikacji oraz 304.

  Przed (`server/index.ts:48–51`):
  ```ts
  const body = await readFile(realFile)
  const cache = path.startsWith('/assets/') ? 'public, max-age=31536000, immutable' : 'no-cache'
  res.writeHead(200, { 'Content-Type': types[extname(file)] ?? 'application/octet-stream', 'Cache-Control': cache })
  res.end(req.method === 'HEAD' ? undefined : body)
  ```

  Po:
  ```ts
  const info = await stat(realFile)
  const etag = `W/"${info.size.toString(36)}-${Math.round(info.mtimeMs).toString(36)}"`
  const cache = path.startsWith('/assets/') ? 'public, max-age=31536000, immutable' : 'no-cache'
  const headers: Record<string, string> = { 'Content-Type': types[extname(file)] ?? 'application/octet-stream', 'Cache-Control': cache, ETag: etag, Vary: 'Accept-Encoding' }
  if (req.headers['if-none-match'] === etag) { res.writeHead(304, headers).end(); return }
  const accepts = String(req.headers['accept-encoding'] ?? '')
  // Pliki .br/.gz tworzy krok po vite build; brak wariantu = plik zwykły.
  const variant = accepts.includes('br') ? '.br' : accepts.includes('gzip') ? '.gz' : ''
  const body = variant ? await readFile(realFile + variant).then((b) => { headers['Content-Encoding'] = variant === '.br' ? 'br' : 'gzip'; return b }, () => readFile(realFile)) : await readFile(realFile)
  res.writeHead(200, headers)
  res.end(req.method === 'HEAD' ? undefined : body)
  ```
  Prostsza alternatywa dla `/data/`: nazwy z hashem treści (`catalog.<hash>.json`, mapa w `index.html` lub w manifeście) z `immutable`. Usuwa potrzebę rewalidacji w ogóle.
- **Ryzyko zmiany.** Małe. Testy w `productionServer.test.ts`: 304 przy zgodnym `If-None-Match`, `Content-Encoding` przy istniejącym wariancie i fallback bez wariantu.

## Wpływ między zakładkami

1. **Pamięć.**
   - Zakładki nie kumulują pamięci. `<main key={tab}>` (`App.tsx:58`) odmontowuje widok, co potwierdził pomiar: po 5 pełnych cyklach zakładek (25 przełączeń) sterta wynosi 38,9 → 39,3 MB, listenery stoją na 410, a żywy jest jeden kontekst WebGL.
   - Okno 3D jest jedynym miejscem narastania (C01). Wyciek dotyka całej aplikacji: dłuższe pauzy GC odczuwa też Katalog i Planer, a na telefonie system ubije kartę.
2. **GPU.**
   - Przy otwartym oknie 3D żyją jednocześnie kontekst kopuły (gwiazdy i do 128 MB zdjęć), Space3D i, przy zdjęciu, Obserwatorium (C10).
   - Limit kontekstów przeglądarki jest daleko. Ważniejszy jest łączny budżet pamięci na zintegrowanym GPU, bo tekstury kopuły nie są zwalniane na czas okna.
3. **Wątek główny.**
   - Kopuła jest najdroższym konsumentem (C02). Na Niebie z kopułą rywalizuje wykres wysokości, bo przeciąganie po nim przesuwa czas i przerysowuje kopułę przy każdym ruchu.
   - Zapis projektu zdjęcia (klon kilku MB, C06) i składanie własnych zdjęć (C07) idą na tym samym wątku. Mogą zbiec się z przerysowaniem albo z rozkładaniem w Obserwatorium.
   - Pod oknem 3D kopuła nie rysuje (0 rAF/s, odtwarzanie zatrzymane), co jest poprawne.
4. **Koszt powrotu do zakładki.** Każdy powrót na Niebo tworzy nowy kontekst WebGL kopuły, liczy noc w ok. 10 instancjach `useNight` (K4, N8) i dekoduje tekstury zdjęć od nowa. Każdy powrót do Katalogu to pełny przebieg workera widoczności (C12). Koszty jednorazowe; 25 przełączeń dało w headless 8 długich zadań.
5. **Serwer jednoprocesowy.** C09 zatrzymuje wszystkie żądania, także statyki, więc dotyka każdej zakładki i każdego klienta. Kolejka regresora (C08) zajmuje CPU w tle długo po zmianie zdjęcia.
6. **Sieć.** C04 kosztuje przy każdym starcie, niezależnie od zakładki. C11 rośnie z liczbą miniatur w Katalogu i Planerze.
